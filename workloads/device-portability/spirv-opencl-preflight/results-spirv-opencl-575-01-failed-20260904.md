## Outcome

This is a **valid negative capability result, not device-kernel execution
evidence**. The original runner status is `invalid` because the pre-capability
runner treated every nonzero demo exit as an infrastructure failure. The
independent analyzer can nevertheless replay the retained terminal outcome and
reports `run_status: valid`, `tested_hypothesis: contradicted`.

The source-native bpftime demo generated 540 bytes of SPIR-V, patched the module
to 528 bytes, selected the RTX 5090, and called `clCreateProgramWithIL`. Program
creation returned `-59` before `clBuildProgram`, kernel creation, or kernel
execution:

```text
Failed to create program from SPIR-V (error code: -59)
Your OpenCL implementation may not support SPIR-V IL
```

The retained 528-byte module independently passes `spirv-val` and
`spirv-dis`; it contains one `bpf_main` kernel entry point, one Physical64
OpenCL memory model, and one function. This supports only a host-side code
generation and structural-validity statement. `clCreateProgramWithIL` did not
create a program and no GPU kernel ran.

## Capability boundary

Khronos defines `-59` as `CL_INVALID_OPERATION` and specifies that
`clCreateProgramWithIL` returns it when no device in the context supports
intermediate-language programs. Khronos also says an OpenCL device reports
supported SPIR-V versions through `CL_DEVICE_IL_VERSION` or
`CL_DEVICE_ILS_WITH_VERSION`, that an empty result means no IL-program support,
and that OpenCL 3.0 does not require SPIR-V support:

- [Khronos `clCreateProgramWithIL` reference](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clCreateProgramWithIL.html)
- [Khronos `clGetDeviceInfo` reference](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clGetDeviceInfo.html)
- [Khronos OpenCL SPIR-V environment](https://registry.khronos.org/OpenCL/specs/unified/html/OpenCL_Env.html)

The same host reports empty `CL_DEVICE_IL_VERSION`, an empty
`CL_DEVICE_ILS_WITH_VERSION` list, and no `cl_khr_il_program` extension. NVIDIA
documents driver 575.57.08 as exposing OpenCL 3.0; that API version alone is
therefore not evidence of SPIR-V ingestion support. NVIDIA staff also
explicitly documented that NVIDIA's OpenCL 3.0 implementation did not support
SPIR or SPIR-V when the 3.0 support was introduced; the attempt-01 error and
current device queries, rather than that historical statement alone, establish
the R575 result:

- [NVIDIA R575.57.08 release notes](https://docs.nvidia.com/datacenter/tesla/tesla-release-notes-575-57-08/index.html)
- [NVIDIA OpenCL 3.0 SPIR-V support statement](https://forums.developer.nvidia.com/t/nvidia-is-now-opencl-3-0-conformant/174942/8)

Attempt 01 did not record these three queries before starting the demo. The
runner now does so and fails closed before host generation or demo execution
unless the selected device explicitly advertises SPIR-V. The original
`result.json`, `execution.json`, `positive.log`, and SPIR-V module are retained
unchanged; only `analysis.json` was regenerated by the hardened analyzer.

## Safety and claim boundary

No owned process survived. The boot was unchanged, and the retained before and
after records contain no Xid, abnormal kernel message, UVM reference, or
`struct_ops` residue.

This attempt cannot support a runnable SPIR-V device backend, a gpubpf
