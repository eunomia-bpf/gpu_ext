# RTX 5090 STRICT uniform-map placement

## Outcome

- Run status: **valid**
- Tested hypothesis: **inconclusive (mixed by operation)**
- Research value: **supporting**
- Paper impact: **additional RQ4 mechanism evidence and a strict-admission
  boundary**

The current STRICT verifier, CUDA JIT, attach path, and GPU runtime execute all
five uniform callbacks end to end. Device-global lookup is faster than the
operation-matched host-mapped lookup in this workload, but update shows no
detected placement difference. Therefore the predeclared joint hypothesis is
not supported.

| Metric, paired median | device-global | host-mapped | host/device effect |
|---|---:|---:|---:|
| Update latency, us/launch | 3.860250 | 3.882750 | 1.0008x [0.9891, 1.0143] |
| Lookup latency, us/launch | 3.841500 | 4.148250 | 1.0778x [1.0644, 1.0833] |

Intervals are 97.5% paired-bootstrap intervals over 12 complete randomized
blocks (10,000 resamples); the two co-primary intervals provide at least 95%
family-wise coverage. Absolute paired effects are +0.003250 us
[-0.042500, +0.055000] for update and +0.298500 us
[+0.251000, +0.319000] for lookup.

The descriptive arm medians are native 2.014250, strict no-op 3.928500,
device update 3.860250, host update 3.882750, device lookup 3.841500, and host
lookup 4.148250 us/launch. Device-minus-no-op arithmetic contrasts can be
negative in this small timed region; they do not estimate a negative map cost
or a causal speedup from adding an operation.

## Strict execution and correctness gates

The full command was:

```sh
python3 run_strict_uniform_map.py --phase full \
  --output raw/strict-uniform-map-full-575-01
python3 analyze_strict_uniform_map.py \
  raw/strict-uniform-map-full-575-01
```

The run used RTX 5090, driver 575.57.08, CUDA 12.9, and the verifier-enabled
CUDA/LLVM build at bpftime revision `04007fc`. All 72 scheduled arms ran in
fresh processes without retry. Independent replay reopened 256 raw files and
accepted:

- 72/72 exact CUDA output records;
- 60/60 target transformations, patched module loads, and attaches;
- 60/60 target-PID `mode=STRICT` acceptance records and positive verifier
  timing records, with zero reject, skip, or verifier-unavailable record;
- 180 exact verified-map descriptor records: every attached program saw two
  type-1503 maps and one type-1513 map, all with 4-byte keys, 8-byte values,
  and one entry;
- 60/60 loader prime/ready/detach lifecycles and strict agent bootstraps;
- 72 map-effect rows: every update changed the selected zero-initialized source
  to the nonzero update value, and every lookup copied the initialized nonzero
  source value into the zero-initialized device observation map; and
- exact twice-per-position balance for every arm, with no surviving owned
  process or private `fig15_uniform_*` shared-memory segment.

STRICT accepted 12 instances each of the two-instruction no-op, 14-instruction
device/host updates, and 22-instruction device/host lookups. The verifier runs
before the CUDA-event interval, so its one-time admission cost is a gate rather
than an input to the steady-state placement metric.

The six-arm preflight at
[`raw/strict-uniform-map-preflight-575-02/`](raw/strict-uniform-map-preflight-575-02/)
also passes independent replay (6/6 processes and 5/5 STRICT acceptances). The
first preflight remains excluded because its execution TSV header was malformed;
the raw directory and failure report are retained, and attempt 02 restarted all
six arms after the serialization fix.

## Interpretation and claim boundary

This result fills the gap left by the earlier WARNING-mode per-lane placement
run: the unmodified current STRICT verifier admits a deliberately distinct
warp-uniform map policy and the accepted program really reaches the GPU and
changes map state. It does **not** make the earlier lane-varying programs
strict-admissible.

All 32 scalar callbacks use constant key 0 and the same value. Consequently,
the measurement includes same-key contention and end-to-end callback/helper
work; it is not pure memory-access latency. The lookup comparison includes the
same device-resident observation-map update in both arms, so it compares the
end-to-end source-map implementations while holding that sink update fixed;
the type-1513 host path includes its coherence fence and cache behavior. The
idempotent final readback proves a nonzero map effect, not invocation
cardinality. This experiment provides no evidence of warp-leader aggregation,
per-lane disjoint-access safety, verifier soundness, multi-block/grid scaling,
general PCIe bandwidth, or application performance.

The safe paper decision is to state that current STRICT supports this uniform
map class, that host mapping adds a measured lookup penalty here, and that the
update placement effect is unresolved. Do not combine these ratios with the
earlier per-lane Full6 ratios or present the two workloads as repetitions.
In particular, the earlier 9.4307x update ratio used 32 distinct lane-derived
keys, whereas this strict variant makes 32 idempotent, contended writes of the
same value to one key. Reusing one address/cache line can hide placement costs
that distinct per-lane destinations expose; this is a plausible workload
explanation, not a measured causal decomposition. STRICT verification is not
an explanation for the smaller ratio: both placement arms use the same strict
mode, and admission finishes outside the timed CUDA-event interval.
