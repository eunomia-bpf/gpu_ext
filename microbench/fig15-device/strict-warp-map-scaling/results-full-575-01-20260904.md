# RTX 5090 STRICT warp-map key scaling, full campaign 575-01

Date: 2026-09-04
GPU / driver: NVIDIA GeForce RTX 5090 / 575.57.08 (CUDA 12.9, bpftime `9a8af41`,
`build-table1-575-strict`)
Result directory: `raw/strict-warp-scaling-full-575-01`

## Outcome

- Run status: **valid**
- Tested hypothesis: **contradicted**
- Research value: **negative result / mechanism boundary**
- Paper impact: **none — repository evidence only. This result must not be
  presented as a paper-positive finding, and it does not revive the retired
  Fig. 15 warp-aggregation wording.**

Warp-uniform map keys do **not** reduce callback-cost growth as active warps
per block increase. The incremental-ratio estimates cluster around one with no
shape trend — two point estimates sit slightly above one, 1.0058 for
`warp_update/shared_update` at 128 threads and 1.0033 for `shared_update/noop`
at 512 threads — and no cross-shape interval excludes one: the cross-shape
change from 1 to 32 warps per block is
1.0102 [0.9768, 1.0390] for `shared_update/noop`, 1.0060 [0.9915, 1.0604] for
`warp_update/noop`, and 1.0062 [0.9878, 1.0257] for `warp_update/shared_update`
(8 paired blocks each; all intervals contain no change). The only per-shape
interval that excludes one in the predicted direction is
`warp_update/shared_update` at 32 threads,
0.9936 [0.9848, 0.9971] — a single-warp shape where the frozen hypothesis has
no inter-warp contention to reduce. The predicted contention relief at large
blocks is therefore contradicted, and no scaling win is claimed.

All 160 scheduled fresh processes ran with no retry, and the campaign passed
every predeclared gate:

- **160/160** processes exited with a **zero** return code; **zero** nonzero
  codes occur anywhere in the campaign;
- **160 correctness markers**: every process reports its full launched-thread
  CUDA output with zero mismatch (8 warmups plus 128 measured launches each);
- **120/120** attached cells show exactly one target-PID `mode=STRICT`

  every cell.

## Scope and claim boundary

- **Single block per launch.** Every launch is `<<<1, threads>>>` at 32, 128,
  256, 512, or 1024 threads. Nothing here measures multi-block or grid scaling.
- **Scalar per-thread callback.** The target contains one
  `call.uni __bpftime_cuda__kernel_trace, ();` per thread and every lane still
  executes it, so all 32 lanes of a warp still issue the same update. This test
  cannot establish once-per-warp dispatch, warp-leader execution, warp
  aggregation, or constant per-warp trampoline cost.
- **Helper 510 reads the physical PTX `%warpid`.** The final distinct key
  counts 4/4/8/16/32 by shape are SM-local hardware warp-slot identifiers
  reused across the 136 launches of a process, **not** logical CTA warp IDs
  0..(warps-1). The oracle requires at least the requested simultaneous warp
  coverage; it deliberately does not pin which physical slots appear.
- The idempotent final readback proves that the planned map effect happened; it
  does not prove invocation cardinality.
- The two map arms differ in key and therefore destination address only; the
  timed CUDA-event interval still contains trampoline, callback, JIT-loaded
  module, and fence work, so this is an end-to-end callback comparison, not a
  memory-contention decomposition. STRICT verification runs before the timed
  interval and is an admission gate, not a metric input.
- No pooling across shapes and no independent-run test were used. Native-arm
  cells are uninstrumented timing-floor/correctness controls and are excluded
  from the paired effects.
- Results do not extend to application performance, verifier soundness, other
  map types, other GPUs or drivers, or the earlier verifier-disabled per-lane
  and strict-uniform placement campaigns, which must not be pooled with this
  workload.
