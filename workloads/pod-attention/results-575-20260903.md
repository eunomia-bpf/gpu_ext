# POD-Attention: device-BPF operator comparison

Status: **complete, 250/250 formal cells independently audited**. The closed
[full campaign](raw/full-575-01/manifest.json) ran on 2026-09-03,
11:05:35–11:35:24 UTC (recorded safety windows); its coordinator subsequently
exited successfully. All values below come from the five-block full campaign,
not preflight. [Machine-readable analysis](raw/full-575-01/analysis.json) and
[independent raw audit](raw-audit.md) retain the detailed evidence.

## Result and claim boundary

The actual device-BPF implementation executes POD's existing selector inside
real attention kernels. It preserves the hard full-output FP16 comparison
against upstream FlashAttention (FA) and the observed exactly-once work
assignment. This supports this policy's expressibility, with measured cost;
it does not reproduce the full POD serving system.

- BPF versus the matched CUDA-context adapter increases CUDA-event latency by
  **0.51–1.18% in nine shapes**; Llama-3-8B / 192 decreases by 0.44%.
- BPF versus the original inline selector increases latency by **0.59–1.52%
  in nine shapes**; Llama-3-8B / 192 decreases by 0.59%. Each of these pointwise
  intervals excludes one. Host-wall comparisons have the same directions.
  This is neither a zero-overhead nor an equivalence result.
- Against FA two-stream overlap, BPF is faster in seven shapes, but slower
  in Llama / 32 (+5.80%), Yi / 32 (+8.49%) and Yi / 64 (+5.31%). Against FA
  serial, nine intervals favor BPF; Yi / 32 includes one. Fusion benefits
  belong to the upstream POD policy/operator, not a new BPF policy.
- The BPF ten-shape process has a **295.63 s median wall time**, versus
  12.01–14.01 s for the controls. This substantial deployment cost is retained
  separately from steady-state operator timing; it is not an isolated
  initialization measurement.

## What is being compared

| Arm | Implementation and purpose |
| --- | --- |
| `official_serial` | Original FA prefill then decode; non-fused baseline. |
| `official_streams` | Original FA on two joined streams; overlap baseline. |
| `pod_inline` | Original inline CUDA selector, with the common sm_120 safety port. |
| `pod_cuda` | Same POD selection rule through the explicit context and launch bridge; adapter control. |
| `pod_bpf` | Actual device-BPF selector through that context and bridge; device-written choices select the attention branch. |

BPF/CUDA measures the matched BPF path, CUDA/inline exposes adapter cost, and
BPF/inline includes the complete added mechanism path. The bridge is part of
these comparisons, so BPF/CUDA is not an isolated device-call instruction
cost. No host callback, host-JIT selection or C fallback supplies BPF choices.

## Frozen measurement protocol

See the [frozen plan](plan.md). RTX 5090, sm_120, driver 575.57.08, fixed 400 W
power cap; the reports identify PyTorch 2.13.0+cu129 / CUDA 12.9. Ten shapes use
Llama-3-8B/Yi-6B attention (32 query heads, 8/4 KV heads, head dimension 128,
FP16) at decode batches 32/64/96/128/192. Prefill is batch one, length 8192;
decode query length is one, cache extent 8192 with 8191 valid KV positions.
All POD arms use the original automatic `fused_params=15` choice, not
per-arm tuning.

Five randomized paired blocks × ten shapes × five arms give **250 operator
cells in 25 arm processes**. Each cell runs ten warmups and retains 100 timed
observations: 25,000 CUDA-event and 25,000 host-wall samples, with none
discarded. Primary latency is the arithmetic mean of complete-operator
CUDA-event samples, including required resets/combines and both stream joins;
secondary latency is the synchronized host-wall mean. The tables below are
the arithmetic mean of the five cell means, not medians.

Paired ratios use the geometric mean of five block cell-mean ratios.
Intervals use 10,000 whole-block bootstrap draws, seed 20260905, with linear
percentile interpolation. Arm order seed is 20260903; input base seed is
20260904. These are pointwise 95% intervals without multiple-comparison
adjustment, not formal equivalence tests. The 100 launches are not treated as
100 independent blocks. Rounded displayed means are not used to calculate
ratios.

## Numerical, engagement and safety evidence

All 250 hard FP16-arm-versus-FA full-output checks passed with the frozen
`atol=1e-3, rtol=1e-5`. The maximum absolute difference across the full
campaign was **0.00006103515625**, not the zero observed in preflight.

Full FA-versus-FP32 characterization scanned 8,388,608,000 prefill and
104,857,600 decode elements across 250 cells. Prefill recorded **150 threshold
exceedances in 100 scans**, maximum absolute error 0.0013279914855957031;
decode recorded zero, maximum 0.000040277838706970215. These totals include
repeated inputs across arms/blocks. The four affected shapes are Llama / 32
(one element per scan), Yi / 32 (three), Yi / 96 (one), and Yi / 192 (one).
They are not a full-FP32 pass. All 100 saved worst query/head rows were
independently recalculated from actual Q/K/V in CPU FP64: the largest
FP32-reference/FP64 difference was 5.4265e-7, while all 100 saved FP16 FA rows
still had an FP64 threshold exceedance (maximum 0.001327910378291719).
This checks saved rows, not complete shapes in FP64.

Each POD arm retained **125,280 diagnostic CTA records**, independently
checked for its actual engine, SM-local atomic ticket, global claim,
exhaustion fallback and exactly-once logical mapping. Per arm the expanded
mapping covers 102,400 prefill and 43,520 decode logical CTAs. The BPF records
use device engine 2. Detailed CTA arrays are diagnostic launches; the timed
path checks launch-level counts/errors but does not save another full array
for every timed invocation.

Both adapter arms recorded **5,550 launch-bridge calls**: 50 shape cells ×
(1 diagnostic + 10 warmups + 100 timed launches). Every POD cell records
81,920 dynamic-shared-memory bytes; the adapters check the real CUfunction
limit and opt-in readback. All 25 before/after safety windows and their
continuous telemetry passed; 8,758 telemetry samples reach a maximum 63°C.
All five owned BPF loaders closed and their five distinct private segments
were removed. No global cleanup was used.

Protocol `pod-fp16-upstream-match-v2` treats FP32 excesses as recorded
cross-precision characterization, not the hard FP16 agreement gate. Earlier
v1 failures and the interrupted preflight remain failed/incomplete and
excluded; the [successful preflight 04](preflight-575-04-review.md) is also
excluded from all formal statistics.

These process intervals cover Python/agent/PTX initialization, reference
scans, diagnostics, warmups, all ten shape measurements and client exit.
Loader startup/teardown is separately coordinated. The BPF process wall cost
is not hidden, but neither it nor the preflight process duration isolates
initialization or explains its cause. CUDA-event/host-wall tables measure
steady-state operator invocations, not server cold-start latency.

The performance runtime has the **strict GPU verifier OFF**. Numerical
agreement, engagement and cleanup do not demonstrate strict verifier
admission or general safety. The common safety/launch compatibility port and
explicit context are measured implementation changes. Nineteen runtime
files were inventoried; the Python interpreter binary/version was not. Its
exact recorded path is checked without claiming binary-version verification.

These are upstream real attention operators with synthetic Q/K/V on an
sm_120 compatibility build. They do not establish full-model accuracy,
all-shape FP32 agreement, arbitrary-binary attachment, a new scheduling
policy, or a full Sarathi/POD serving-system reproduction.
