# Strict admission of the Fig. 15 map programs

## Result

Run status: **valid CPU-only admission check**. The current strict GPU verifier
accepts 1 of the 7 real programs in `map_probe.bpf.o`: `cuda__noop`. It rejects
all six map-access programs.

| Real ELF program | Instructions | STRICT result | Rejection class |
| --- | ---: | --- | --- |
| `cuda__noop` | 2 | accept | -- |
| `cuda__device_update` | 20 | reject | varying branch; varying map key and shared-map value |
| `cuda__host_update` | 20 | reject | varying branch; varying map key and shared-map value |
| `cuda__rpc_update` | 20 | reject | varying branch; varying map key and shared-map value |
| `cuda__device_lookup` | 26 | reject | two varying branches; two varying map keys; varying shared-map value |
| `cuda__host_lookup` | 26 | reject | two varying branches; two varying map keys; varying shared-map value |
| `cuda__rpc_lookup` | 26 | reject | two varying branches; two varying map keys; varying shared-map value |

The three update programs have the same rejection sites: the lane-bound branch
at local instruction 3 and the map update at instruction 16. The three lookup
programs have the same sites: branches at instructions 4 and 14, map keys at
10 and 24, and the shared-map update value at 24. The underlying cause is the
program's deliberate use of `bpf_get_lane_id` (helper 511) to issue one access
per lane. The verifier models that result as lane-varying.

All controls behaved as predeclared:

| Control | Expected | Observed |
| --- | --- | --- |
| minimal `r0 = 0; exit` | accept | accept |
| unknown helper 512 | reject | reject: invalid helper function id |
| branch on helper 511 result | reject | reject: lane-varying predicate |
| otherwise-valid program plus map type 1599 | reject | reject: unsupported GPU map type |

## Why the input is faithful

The checked object was the 13,136-byte object built from
`microbench/fig15-device/map_probe.bpf.c` (source commit `c2124bcc`). It contains
one 140-instruction section and seven contiguous `STT_FUNC` symbols with the
2/20/20/20/26/26/26 instruction sizes above. The harness used the verifier's
own `read_elf` path to parse BTF and apply all nine map relocations before
slicing the section at those symbol boundaries.

The complete descriptor table passed to every `verify_gpu_program` call was:

| ELF map | Offline fd | Type | Key/value bytes | Entries |
| --- | ---: | ---: | ---: | ---: |
| `device_values` | 1 | 1503 | 4 / 8 | 32 |
| `host_values` | 2 | 1513 | 4 / 8 | 32 |
| `rpc_values` | 3 | 2 | 4 / 8 | 32 |
| `observed_values` | 4 | 1503 | 4 / 8 | 32 |

The pseudo-fd values are the verifier ELF reader's offline relocation values;
map type, dimensions, capacity, and each program's map association are
preserved. Helpers remain the real ELF immediates and resolve through the
current GPU helper model as `bpf_map_lookup_elem` (1),
`bpf_map_update_elem` (2), and `bpf_get_lane_id` (511).

The isolated Release build used bpftime `c1c4cf6`. The real built-probe test
passed all four test methods with `CUDA_VISIBLE_DEVICES` empty. The raw result
is [`raw/admission-c1c4cf6.json`](raw/admission-c1c4cf6.json).

## Interpretation and boundary

This result closes a labeling gap. The completed map-tier experiment genuinely
executed these programs on the GPU in verifier **WARNING** mode, but its six
map arms are not accepted by the current STRICT model. The latency result
remains valid for that execution mode; it must not be described as strict
verifier-gated evidence.

Making this per-lane microbenchmark strict-compatible would require either a
different warp-uniform access policy or a verifier refinement that proves
disjoint per-lane map accesses safe. The former changes the measured workload,
so it must be a separate experiment rather than a silent repair of the existing
map-tier comparison.

This harness invokes only the CPU `verify_gpu_program` API. It performs no GPU
load, JIT, attach, or execution and makes no claim about runtime fd allocation,
GPU execution safety, attach safety, or verifier soundness.
