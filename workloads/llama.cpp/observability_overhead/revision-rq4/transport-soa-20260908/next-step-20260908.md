## Reviewed analysis

The original object emits per-thread 80-byte payloads with 256 entries per
thread. The allocated ring is 11,823,743,008 bytes. Its per-thread headers
and records are far apart in the current layout. A transpose can change
memory-access layout without sampling or dropping observations.

The runtime does **not** collapse this original event program to one call
per warp. In bpftime `241872b`,
`bpftime-verifier/src/gpu/warp_execution_eligibility.cpp` explicitly rejects
helper 25 (`bpf_perf_event_output`) for that transformation.
`nv_attach_impl.cpp` only enables leader lowering after eligibility succeeds.
The requested auto-execution environment also selects ring transport, which
is a separate optimization. Root rejected the local read-only analysis's
contrary claim that this program's on arm executes only a warp leader.

Similarly, 44 launches times 524,288 slots gives 23,068,672 **expected**
per-thread events for the assumed timing geometry, not an observed final
collector count. The latter is unavailable in the completed campaign.
The old warp-level campaign's 720,896 events are recorded observations.

All twenty new loaders exit -9 after successful benchmarks. The existing
helper sends SIGINT, waits eight seconds, sends SIGTERM, waits five seconds,
then SIGKILL. The collector performs a final drain and a full-array coordinate
sort before reporting. That potentially expensive post-processing is a
plausible cause of exceeding the allowance, but the silent existing logs do
not locate where it was killed. No claim of a proven drain deadlock or proven
sort bottleneck is made; no diagnostic replay is scheduled. Future performance
collection should avoid imposing a short stop deadline on useful post-exit
work and should not require the unrelated full coordinate sort.

## Implementation still needed

The existing `host-transport-soa.patch` passes `git apply --check` against
current bpftime `241872b`. It has **not** been applied alone: the companion
device writer is missing, so mode 3 is not yet runnable.

Mode 3 keeps the same capacity, size word, per-thread event order, full/drop
behavior and encoded publication protocol. It packs the 24-byte headers
together and transposes payload words so adjacent thread IDs write adjacent
eight-byte locations. The host reconstructs every payload before invoking
the unchanged record callback. Modes 0/1/2 remain unchanged.
